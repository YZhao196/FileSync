# FileSynapse — mobile client

A viewer and browser for a FileSynapse server, on a phone. React Native + Expo,
per PLAN.md §11.

**It does not upload, ever.** Camera upload is Immich's own app doing background
work that this project has no intention of reimplementing, and UI-MOBILE.md
states the rule twice because it is load-bearing. There is no upload method on
the backend interface, so it is enforced by construction rather than by
intention.

```bash
npm install
npm start                  # Expo dev server; needs a dev client, not Expo Go
npm test                   # jest
npm run typecheck
npx expo prebuild -p android   # generate the native project
```

Requires a **development build**, not Expo Go: `expo-secure-store`,
`expo-file-system`, the SVG icon layer and the cleartext-HTTP configuration are
all native. `android/` and `ios/` are generated by `prebuild` and are not
committed.

## How it shares code with the desktop

`src/core/` and `src/lib/` are **copies** of `app/src/core/` and `app/src/lib/`,
enforced by `scripts/sync-core.mjs` — which CI runs in `--check` mode, so the two
cannot drift without failing the build. A workspace package would have been the
obvious alternative and was rejected on purpose: it would move the lockfile to
the repo root and make `app/` depend on something outside its own directory,
which is a documented convention (see PLAN.md §13.3).

Nothing is rewritten on the way across, which is what makes the drift check a
plain byte comparison. Three things make that possible:

- **`src/native/bridge.ts`** answers `remote.ts`'s `../native/bridge` import,
  because this directory mirrors the desktop's layout. React Native's `fetch` is
  not subject to origin enforcement, so where the desktop needs a Rust command
  to dodge CORS, this needs nothing.
- **`src/platform/polyfills.ts`** supplies `DOMParser`, `URL`, `TextEncoder` and
  `btoa`. It is imported first from `index.ts`, before anything that needs them.
- **`test/vitest-shim.js`** aliases the `vitest` import in the copied tests onto
  Jest, so the desktop's own assertions run here unmodified. That is the point:
  the shared logic is verified on both platforms by the same tests rather than by
  two suites that drift apart.

The desktop's tests caught a real difference the first time they ran here.
xmldom throws on malformed XML where jsdom returns a document, and
`parseMultiStatus` depends on the lenient behaviour. `polyfills.ts` wraps the
parser; the divergence that survives is documented in that file.

## What is generated

`src/theme/tokens.generated.ts` comes from the desktop's
`app/src/styles/tokens.css`, and `src/components/icons.generated.ts` from
`@carbon/icons`. Both are committed and both have a `--check` mode that CI runs,
because a generated file that is stale looks exactly like a correct one.

```bash
node scripts/gen-mobile-tokens.mjs
node scripts/gen-mobile-icons.mjs
```

`@carbon/icons` is a devDependency — read at generation time, never bundled. Its
install runs IBM's telemetry, which `allowScripts` in `package.json` denies, for
the same reason the desktop denies it.

## What exists

|---|---|
| First Run | Address and credentials, per-backend validation, stored in the OS keystore |

| Files | Browser with a breadcrumb; folders first |
| Settings | Server, Account, About; Disconnect removes everything stored |

## What does not

The photo viewer, multi-select, search, albums, file preview and file actions,
and the Appearance, cache and About settings. These are **absent rather than
stubbed** — a control that does nothing teaches the reader to distrust the ones
that work.

## The honest position

Nothing here has touched a live Immich or Nextcloud. The mock backend is what
renders, and `src/core/client.ts` selects it in a development build and cannot
reach it in a release one — the same guarantee the desktop gets, through
`__DEV__` rather than `import.meta.env.DEV`.

Two things in particular are unverified and cannot be settled by reading:

- **Cleartext HTTP on a device.** The whole backend is plain `http://` over
  Tailscale. Android blocks cleartext by default and iOS ATS blocks non-HTTPS;
  `expo-build-properties` is configured for both, and if that configuration is
  wrong **every request fails** and no amount of mock testing reveals it.
- **WebDAV verbs through React Native's fetch.** `PROPFIND`, `MKCOL` and `MOVE`
  with `Depth` and `Destination` headers are non-standard, and Android's HTTP
  stack has historically been the fussy one.

iOS is **not buildable here**. An unsigned iOS build is Simulator-only, and the
Simulator needs macOS. There is no Mac, so there is nothing to build.
